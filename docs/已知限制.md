# 已知限制

本文件逐条列出**已确认存在、且短期内不会修复**的限制，以及每条限制的成因。提 Issue 前请先对照本文件。

信息以抖音 **31.7.1 / 38.6.0 / 40.x** 的实测为准，每条限制内会注明具体版本。

---

## 一、信息流广告：只在数据进入 Adapter 之前清理，其余一律放行

**现象**：开启「广告拦截」后仍可能刷到广告，且出现时会正常播放；其中优惠券、商品卡片这类内容从来不会被拦截。

**原因**：只在数据交给 Adapter 之前清理，共两处：

1. **数据源回调**：DexKit 定位 `recommendFeedFetchPresenter` / `fullFeedFollowFetchPresenter`，在 `onSuccess` 里把当页列表整体替换。
   抖音 **31.7.1** 实测命中 `X.V76` / `X.V4N`；**38.6.0 两个 matcher 均为 `null`**，该层自动退化为不生效（无副作用）。
2. **数据落表**：`setData(List)` / `setData(List, boolean)` —— 31.7.1 与 38.6.0 实测都是这个**未混淆**的名字；40.x 对应的是混淆名 `LJLILLLLZI` / `LJLJI`。
   代码里两套名字同时挂着，哪套存在就绑哪套（xpler 按名绑定，绑不上只记一行日志）。

判定统一按 `Aweme.isAd`（序列化名 `is_ads`）。

以下情况一律**不改数据、不做隐藏**，按官方流程正常播放：

- 目标类/方法未命中（日志里只有「已注册」，没有「整表 N 项」或 `path for`）；
- presenter 的列表字段无法定位（`skipped (no access path)`）；
- 清理会把整表删空 —— 宿主把「空表」当成「替换整表但不 notify」，pager 期望数量会永久过期；
- 经增量接口（`LJJLIL` / `LJJLJ` 一类）插入的项，完全不处理；
- **未带 `isAd` 标记的推广内容，例如优惠券、商品卡片**。

**优惠券 / 商品卡为什么删不掉**：38.6.0 实测，出现优惠券时 `setData` 收到的是 46~58 条的完整列表，`isAd` 全为 `false` —— 这类内容不带广告位标记，或者根本不经过整表接口。要覆盖它们只能改插入接口的入参、或另找标记字段，属于历史上已经崩过的方向（见下），因此不做。

放行是刻意设计，不是遗漏（历史事故见 [v1.3.9 PagerAdapter 崩溃修复](修复说明-v1.3.9-PagerAdapter崩溃.md)）。早期版本在 `VideoViewHolder.bind` 前置阻断，会让 `mFeedItemFragmentVM` 为 null，切 tab 必崩；后来改成「绑定后隐藏」，又留下空白页且可能只听到声音；再后来尝试在 `notifyDataSetChanged()` 前删项，因 Adapter 存在不可达的列表副本而条数/item 失配，`getView` 拿到 null（黑屏 + `setActivityId` 空指针）。以上三种做法均已下线。

**判定逻辑依据**（已通过字节码确认）：

```
Aweme.getAd()        = isAd && awemeRawAd != null
Aweme.getIsAdAweme() = isAd
```

**如何自验**（业务日志用的是类名 tag，不是 `Freedom+`）：

- `adb logcat -s HFeedAdFilter`：`整表 N 项, 剔除广告 M 项`（命中）或 `整表 N 项, 未发现广告`（本页无目标项）；
- `adb logcat -s HFeedSourceFilter`：`path for ...`（路径解析成功）、`removed N/M at source (total K)`（确实剔除）、`skipped (...), source data left untouched`（放弃处理）。

`HFeedSourceFilter` 只在 31.7.1 上有输出；38.6.0 上该层不注册，属预期（整数表路径覆盖翻页）。

## 二、小程序 / 小游戏广告的「跳过展示」链路在 40.6.0 上退化为不生效

**现象**：日志中出现 `T5-miniapp: no operate* method, skipped`。

**原因**：该链路依赖拦截 `operateInterstitialAd` / `operateVideoAd` 等方法。抖音 40.6.0 已把这些方法名混淆（例如 `operateInterstitialAd` → `LJII`），按方法名匹配无法命中。

**当前处理**：代码按 `operate*` 前缀匹配，40.6.0 上匹配不到就明确记日志并跳过（**不会误伤其它方法**）。小程序广告由「广告类型总开关」（L1）兜底拦截。

## 三、底部控制栏相关能力在 40.6.0 上语义已不成立

**现象**：与「底部控制栏」相关的隐藏 / 移除功能在 40.6.0 上无效果。

**原因**：早期版本中底部控制栏是**单一容器 ViewGroup**，移除该容器即可整体隐藏。40.6.0 已把它**拆散成多个独立 View**，承载进度条的是标准 `android.widget.FrameLayout`，不存在当年的单一容器。

**证据**：运行时 View 树探针确认；静态核对也支持该结论 —— `IPauseCtrlAction` 在 38.7.0 与 40.6.0 上都不存在，`@Signature` 注解实例数为 0，`LX/` 下的 FrameLayout 子类多达 863 个，无法收敛到唯一目标。

该 matcher 属于「语义失效」，不是「还没修」。

## 四、40.6.0 下仍有 7 个 DexKit matcher 未命中

DexKit 匹配命中数从初始的 7 / 25 提升到 18 / 25，剩余 7 个每条都有明确归因：

| 未命中项 | 归因 |
|---|---|
| `recommendFeedFetchPresenter` / `fullFeedFollowFetchPresenter` | 原有的信息流过滤链路在 40.6.0 整体不存在（相关类已移除，持有 `FeedItemList` 的 55 个类中没有一个包含 `onSuccess`，`items` 字段无写入点可 hook）。**已由新的 adapter / ViewHolder 方案替代** |
| `coenerExtendsionsPoupWindow` | 40.6.0 已无对应弹窗（原用于在抖音内注入模块设置入口）。不影响核心功能 |
| `bottomCtrlBar` | 见上一条「底部控制栏」，语义失效 |
| `chatListRecyclerViewAdapter` | **故意保留旧特征使其失败**。它与 `chatListRecyclerViewAdapterNew` 指向同一个目标类，hook 逻辑等价；同时命中会导致列表项被插入两个 TextView |
| `longPressEvent` / `doubleClickEvent` | 分析中 |

## 五、抖音版本适配的固有脆弱性

抖音每个版本都会重命名、混淆内部类。本项目以**未混淆的类 / 方法 / 字段**为锚点，并用 DexKit 做特征匹配，因此在混淆名漂移时具备一定自愈能力。已经验证过的例子：

> 广告解析计时功能依赖 `parserField.type` **运行时取类型**，因此不惧混淆名漂移 —— 该混淆名在 38.7.0 时是 `1DN2`，40.6.0 变成 `1Pq5`，功能不受影响。

但以下情况会导致功能**静默失效**（代码会记日志，不会崩溃）：

- 锚点类本身被移除或被混淆；
- 目标方法从子类上移到父类 —— xpler 只检索目标类的 `declaredMethods`，方法上移后 hook 绑不上；
- 目标字段的注解被移除（40.6.0 中 `dalvik.annotation.Signature` 注解实例数为 0，依赖字段注解的匹配规则整体失效）。

遇到「某功能突然没了」，先看日志里对应的 `skipped` 记录，再对照抖音版本号判断。

## 六、只支持 64 位抖音

32 位抖音下模块对部分资源的处理会失败，表现为频繁崩溃。这是已知限制，不做兼容。

## 七、极速版 / 火山版未做完整验证

作用域中已声明 `com.ss.android.ugc.aweme.lite`（极速版）与 `com.ss.android.ugc.live`（火山版），但**未做完整功能验证**，可能出现部分功能不可用的情况。欢迎在 Issue 中反馈具体表现。

## 八、双击视频响应类型：靠「吞掉第二次点击」实现，不 hook 点赞方法

**做法**：在 `com.ss.android.ugc.aweme.feed.ui.LongPressLayout.onTouchEvent` 的 `@OnBefore` 里做手势状态机。第二次 ACTION_DOWN 命中（与上次抬起间隔 ≤ `getDoubleTapTimeout()`、位移 ≤ `getScaledDoubleTapSlop()`、上一次是有效轻点）即判定为双击；「打开评论」模式下把这次手势（DOWN/MOVE/UP）整体 `setResult(true)` 吞掉，抖音侧收不到这次点击，原生点赞不会发生，随后异步点击评论按钮的 contentDescription 打开评论区。「点赞视频」模式或主开关关闭时完全不介入。

**为什么不 hook 点赞方法**：`DexkitBuilder.doubleClickEventClazz` 的 matcher（1 个字段 + `(boolean)` 方法 + `(View, MotionEvent ×3)` 方法，且要求唯一命中）在 40.6.0 全库不成立；38.6.0 上实测点赞始终发生，说明它同样没有命中。把功能绑在这类混淆特征上，换版即失效。

**已知副作用与兜底**：吞掉第二次 DOWN 后，抖音会把这次手势当成「单击」（它的单击确认在抬手约 300ms 后触发），于是**打开评论区的同时视频被暂停**——38.6.0 实测如此。设置里的「打开评论区后暂停播放」就是为它准备的：

- 关闭（默认）：命中双击后补一个 `ACTION_CANCEL` 让抖音的手势状态机复位，撤销待确认的单击；再在 500ms 后检查 `HPlayerController.isPlaying`，确实被暂停了就补一次单击把播放切回来。
- 打开：保留抖音原生的暂停行为。

若某天两种方式都不理想（例如评论面板会吞掉恢复用的合成点击），可把 `HLongPressLayout` 里的 `doubleTapSwallowPolicy` 从 `DOWN_AND_UP` 改成 `UP_ONLY`（只吞 UP）或 `NONE`（不拦点赞、只开评论）。

**自验**：`adb logcat -s HLongPressLayout`（`KLogCat.tagX` 打出的 tag 即传入的 tag），双击后应看到 `双击命中: mode=打开评论, swallow=...` 与 `打开评论成功`；失败时会打 `打开评论失败: 未找到评论按钮` 并附上可用的 contentDescription 列表。
