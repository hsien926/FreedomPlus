# 已知限制

本文件逐条列出**已确认存在、且短期内不会修复**的限制，以及每条限制的成因。提 Issue 前请先对照本文件。

信息以抖音 **40.6.0**、Android 17、小米 M2102K1C 上的实测为准。

---

## 一、信息流广告：删不掉就放行，仍可能刷到广告

**现象**：开启「广告拦截」后，信息流里仍可能偶尔出现广告，且出现时会正常播放。

**原因**：清理只发生在两个确定时机 —— 整表落表（`HFeedAdFilter`）与 `notifyDataSetChanged()` 之前（`HFeedAdNotifySweep`）。以下情况都会**直接放行**（代码保持原样、广告照常播放）：

- DexKit 的 `abstractFeedAdapterClazz` 未命中（日志里只有 `HFeedAdFilter 已注册`，没有「整表 N 项」）；
- 非主线程调用 notify（`FeedArrayList` 有主线程校验）；
- Adapter 上取不到任何 `List` 字段，或清理会把某份列表删空（会触发抖音 `getCount() == 0` 的「整表替换但不 notify」分支，导致 pager 期望数量永久过期）；
- 宿主插入广告后**不调用** `notifyDataSetChanged`。

放行是刻意设计，不是遗漏：删不准宁可不删（历史事故见 [v1.3.9 PagerAdapter 崩溃修复](修复说明-v1.3.9-PagerAdapter崩溃.md)）。早期版本改为在 `VideoViewHolder.bind` 前置阻断，会让 `mFeedItemFragmentVM` 为 null，切 tab 必崩；再后来改成「绑定后隐藏」，又会留下空白页且可能只听到声音。两种都已下线。

**判定逻辑依据**（已通过字节码确认）：

```
Aweme.getAd()        = isAd && awemeRawAd != null
Aweme.getIsAdAweme() = isAd
```

清理时按 `Aweme.isAd`（序列化名 `is_ads`）判定，按对象引用删除（不依赖 `equals`）。

**如何自验**：`adb logcat -s Freedom+`，应能看到

- `HFeedAdFilter: 整表 N 项, 剔除广告 M 项` —— 整表链路是否命中；
- `HFeedAdNotifySweep: 已真删插队广告 N 处(涉及 M 份列表… )` 或 `跳过清理(原因)`。

若刷到广告且上述两类日志一条都没有，说明宿主还有别的广告插入路径或钩子未命中，请附日志提 Issue。

> 注意：以上结论在抖音 **40.6.0** 上验证过；31.x 的混淆名不同，是否命中以日志为准。

## 二、小程序 / 小游戏广告的「跳过展示」链路在 40.6.0 上退化为不生效

**现象**：日志中出现 `T5-miniapp: no operate* method, skipped`。

**原因**：该链路依赖拦截 `operateInterstitialAd` / `operateVideoAd` 等方法。抖音 40.6.0 已把这些方法名混淆（例如 `operateInterstitialAd` → `LJII`），按方法名匹配无法命中。

**当前处理**：代码按 `operate*` 前缀匹配，40.6.0 上匹配不到就明确记日志并跳过（**不会误伤其它方法**）。小程序广告由「广告类型总开关」（L1）兜底拦截。

## 三、底部控制栏相关能力在 40.6.0 上语义已不成立

**现象**：与「底部控制栏」相关的隐藏 / 移除功能在 40.6.0 上无效果。

**原因**：早期版本中底部控制栏是**单一容器 ViewGroup**，移除该容器即可整体隐藏。40.6.0 已把它**拆散成多个独立 View**，承载进度条的是标准 `android.widget.FrameLayout`，不存在当年的单一容器。

**证据**：运行时 View 树探针确认；静态核对也支持该结论 —— `IPauseCtrlAction` 在 38.7.0 与 40.6.0 上都不存在，`@Signature` 注解实例数为 0，`LX/` 下的 FrameLayout 子类多达 863 个，无法收敛到唯一目标。

该 matcher 属于「语义失效」，不是「还没修」。

## 四、40.6.0 下仍有 7 个 DexKit matcher 未命中

DexKit 匹配命中数从初始的 7 / 25 提升到 18 / 25，剩余 7 个每条都有明确归因：

| 未命中项 | 归因 |
|---|---|
| `recommendFeedFetchPresenter` / `fullFeedFollowFetchPresenter` | 原有的信息流过滤链路在 40.6.0 整体不存在（相关类已移除，持有 `FeedItemList` 的 55 个类中没有一个包含 `onSuccess`，`items` 字段无写入点可 hook）。**已由新的 adapter / ViewHolder 方案替代** |
| `coenerExtendsionsPoupWindow` | 40.6.0 已无对应弹窗（原用于在抖音内注入模块设置入口）。不影响核心功能 |
| `bottomCtrlBar` | 见上一条「底部控制栏」，语义失效 |
| `chatListRecyclerViewAdapter` | **故意保留旧特征使其失败**。它与 `chatListRecyclerViewAdapterNew` 指向同一个目标类，hook 逻辑等价；同时命中会导致列表项被插入两个 TextView |
| `longPressEvent` / `doubleClickEvent` | 分析中 |

## 五、抖音版本适配的固有脆弱性

抖音每个版本都会重命名、混淆内部类。本项目以**未混淆的类 / 方法 / 字段**为锚点，并用 DexKit 做特征匹配，因此在混淆名漂移时具备一定自愈能力。已经验证过的例子：

> 广告解析计时功能依赖 `parserField.type` **运行时取类型**，因此不惧混淆名漂移 —— 该混淆名在 38.7.0 时是 `1DN2`，40.6.0 变成 `1Pq5`，功能不受影响。

但以下情况会导致功能**静默失效**（代码会记日志，不会崩溃）：

- 锚点类本身被移除或被混淆；
- 目标方法从子类上移到父类 —— xpler 只检索目标类的 `declaredMethods`，方法上移后 hook 绑不上；
- 目标字段的注解被移除（40.6.0 中 `dalvik.annotation.Signature` 注解实例数为 0，依赖字段注解的匹配规则整体失效）。

遇到「某功能突然没了」，先看日志里对应的 `skipped` 记录，再对照抖音版本号判断。

## 六、只支持 64 位抖音

32 位抖音下模块对部分资源的处理会失败，表现为频繁崩溃。这是已知限制，不做兼容。

## 七、极速版 / 火山版未做完整验证

作用域中已声明 `com.ss.android.ugc.aweme.lite`（极速版）与 `com.ss.android.ugc.live`（火山版），但**未做完整功能验证**，可能出现部分功能不可用的情况。欢迎在 Issue 中反馈具体表现。
