# 已知限制与适配边界

本文对应 FreedomPlus **v1.4.0**。功能总览见[项目首页](<../README.md>)；以下区分当前实现边界、历史 40.6.0 诊断记录与尚未完成的验证，不能把某次类匹配成功当作全功能可用证据。

## 一、信息流广告仍为实验性

当前仅在可验证的响应源列表中剔除 `isAd` 项；列表必须具有唯一、匹配的元素结构，且允许安全替换字段引用。模型尚未初始化会重试，坏迭代器、不可写字段、具体集合类型不兼容或全广告表都保持源数据不变。

旧 Adapter 逐份修改平行列表及三处 ViewHolder `bind` 阻断已经停止。没有可证明安全的最外层整表写入契约时，Adapter 入口只记录首次诊断并原样放行；不修改计数、不操作通知、不以空白页隐藏广告。

历史测试累计观察 250 次 bind，`isAd=true` 数量为 0，因此没有真实投放下的成功拦截证据。31.7.1 数据源 matcher 的命中来自 PR 作者测试；38.6.0 / 40.x 缺少安全数据入口时可能仍显示广告，不能把“注册成功”写成“广告已去除”。SDK 广告链路仍独立处理，不关闭全局广告开关。

## 二、小程序 / 小游戏的部分展示入口缺失

历史 40.6.0 记录出现：

```text
T5-miniapp: no operate* method, skipped
```

这条展示链路依赖 `operateInterstitialAd` / `operateVideoAd` 等名称，40.6.0 下名称混淆后无法匹配，记录日志并跳过。匹配到的 SDK 类型总开关、插屏、激励计时等链路仍独立处理，不等同于每条入口都有效。

SDK 类型列表中的开屏、横幅、贴片等名称描述的是对应 SDK 请求，不是对所有抖音启动广告的拦截保证。激励视频的本地计时 / 关闭处理也不保证目标服务端发放奖励。

## 三、非广告视频过滤在 40.6.0 下不能视为恢复

设置中保留直播、图文、长视频、推荐卡片、推荐商家、空文案和文案关键字等规则。

但旧 `recommendFeedFetchPresenter` / `fullFeedFollowFetchPresenter` 数据入口在 40.6.0 下缺失。新的 Adapter / ViewHolder 方案处理的是广告，不是这些非广告类型的统一替代实现；不能从“广告方案已重构”推出“所有过滤规则已恢复”。

### PR #3 数据源过滤补充

- 推荐 / 关注源的 onSuccess 只替换唯一、已验证且可写的列表；其余情况放行。
- `setData`、`LJLILLLLZI`、`LJLJI` 保留诊断入口，未知 Adapter 布局不再尝试过滤。
- 本次新增 JVM 回归确认失败不会清空原列表；没有重新开展上述宿主版本的真机投放测试。

## 四、旧界面容器与入口随版本变化

- **底部播放控制栏**：旧版是单一 ViewGroup，40.6.0 已拆成独立 View，旧整体移除逻辑不再适用。
- **旧加号弹窗 / 侧边栏**：保留实现，但目标版本中对应界面可能已移除，不能作为通用设置入口。优先使用长按视频上半屏或模块应用中的跳转入口。
- **双击响应**：按 View 和视频身份隔离状态，在第二次 DOWN 前判断。默认保持播放的接管路径会恢复原事件并发送 CANCEL 收尾，不再延时模拟播放；未知视频身份、过窄布局或找不到唯一可见评论入口时保留原生响应。取消、多指、页面切换使待执行动作失效。新链路未独立完成真机回归，不保证所有版本的播放状态和原生点赞均符合预期。
- **清爽与沉浸布局**：取决于目标视频页面的控件结构，部分内容可能出现裁切、拉伸或控件恢复不完整。
- **图片转换**：VVIC / HEIC 图文需要宿主内置解码器，解码器缺失或解码失败时不保证成功转为 JPEG。

## 五、保留设置与未接入代码

| 项目 | v1.4.0 的实际状态 |
|---|---|
| 消息防撤回 | 保留开关及“保留自己撤回的消息”设置，页面标注“失效不修”；不恢复服务端已替换的内容 |
| 语音评论保存 | 工具类保留在源码中，但未接入可触发入口，不列为当前已可用功能 |
| 崩溃容错 / 去插件化设置 | 处于暂存区，当前设置页不展示；不把历史菜单列为普通可用开关 |
| WebDAV | 当前是视频、图片、背景音乐的下载后上传，不是模块配置备份 / 恢复 |

## 六、高刷新率边界

- 应用侧与小米 PowerKeeper 系统侧集成在同一个 APK，系统侧需启用 `com.miui.powerkeeper` 作用域。
- 新装默认关闭；升级首次迁移主抖音内的既有开关。
- 应用侧按进程启动时开关注册，改开关后需重启抖音；首次追加系统作用域还需重载 PowerKeeper 主进程。
- 系统侧基于已核对的 PowerKeeper **4.2.00**。类、方法或必需字段不匹配时保留系统原策略。
- 不修改其它应用、副屏、全局刷新率键、视频源帧数、时间戳或播放速度。
- 保留省电、中等及以上热状态限制、用户上限及其它系统投票。不禁用温控服务。
- 直接 native 帧率调用、特定私有系统策略、未重新提交的 Surface 意图不在新增保证范围内。
- 已有小米设备反馈确认界面高刷生效，不扩展为所有 ROM、所有视频源、锁屏 / 重启持久性均已验证。

详细说明及对照检查见[高刷新率说明](<高刷新率.md>)。

## 七、客户端、框架与适配列表

- 以 64 位主抖音和 LSPosed 为基准，32 位不作兼容保证。
- 极速版 / 火山版保留加载规则，未完成完整验证，也不使用主抖音共享系统侧高刷开关。
- [包内适配列表](<../app/src/main/assets/versions.json>) 包含 28.x、29.x、30.0.0–30.3.0 中列出的版本及 40.6.0；不是 28.0.0 到 40.6.0 的连续全区间支持声明。
- 最低构建要求 API 24 对应 Android 7.0，不代表每项功能均在该系统测试；公开 Java Surface 高刷处理要求 Android 11+。
- 版本提示“功能正常”只表示列表命中，不是每个功能均已验证。

抖音持续修改内部类与方法。特征锚点消失、方法迁移到父类、字段注解变化都可能导致目标路径跳过；按日志及具体版本逐项判断。
