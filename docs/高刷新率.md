# FreedomPlus 1.3.12 · 双进程高刷新率

## 当前结论

1.3.12 把应用侧与小米 PowerKeeper 系统侧处理放在同一个 APK 中，沿用原“解锁高刷新率（实验）”开关，不需要另装桥接模块；发布保留规则已修正，两个进程的 Xposed 回调执行体不再被 R8 删除。

2026-11-15 已有小米设备安装使用反馈：1.3.12 的抖音界面高刷已生效。该结论来自实际使用反馈，不是新增 ADB 测量，也不扩大为所有 ROM、所有视频源或重启持久性均已验证。此前系统侧切入点与字段来自已核对的 PowerKeeper 4.2.00 原始 DEX。

## 启用

1. 安装 1.3.12 发布 APK，保留原抖音数据与模块设置。
2. 在 LSPosed 中保留 `com.ss.android.ugc.aweme`，追加 `com.miui.powerkeeper`（电量与性能）。
3. 打开一次 FreedomPlus 应用，使模块提供方处于可启动状态。
4. 在抖音内打开原“解锁高刷新率（实验）”开关。升级首次读取抖音原有开关，不把模块应用里的默认值当作迁移来源；新装默认关闭。
5. 强制停止并重新打开抖音。第一次追加系统作用域还要重载 PowerKeeper 主进程；只重开抖音不会使已运行的系统进程加载新 Hook。整机重启是明确重载全部相关进程的方式，本次开发并未执行。

应用侧仍按进程启动时的开关决定是否注册 Hook。设置页更改开关后保留原重启提示，不宣称已经运行的应用侧 Hook 会立即全部撤销。

## 回退

1. 关闭原高刷开关并重启抖音。
2. 系统侧会同步读取关闭值；如果仍处于同一个抖音主屏视频场景、同一 cookie 和原 Looper，可回放最近的原始视频请求；场景已经变更则不回放旧请求。
3. 若要完全退出系统侧处理，在 LSPosed 中取消“电量与性能”作用域，然后重载 PowerKeeper 或重启手机。取消勾选本身不会移除已运行进程中的 Hook。
4. 不需要恢复 `miui_refresh_rate` 等全局键：本功能没有直接写入这些键。
5. 通过关闭开关、取消新增作用域并重载相关进程恢复原路径，不需卸载或清空抖音数据。

## 两条初始化路径

```text
FreedomPlus 1.3.12
├─ 抖音主进程：原插件、资源注入、MMKV、DexKit和其它功能保持原样
│  └─ 原高刷开关 → 窗口模式与公开Java Surface请求
└─ PowerKeeper主进程：独立系统高刷Hook
   └─ 同一个共享开关 → 仅改抖音主屏正常视频低刷新率请求
```

PowerKeeper 分支在原抖音初始化入口之前返回，不能运行抖音的插件、资源注入、MMKV 或 DexKit。其它已支持的抖音包仍走原加载规则；极速版与火山版不使用主抖音的共享系统侧开关。

## 共享开关

模块内受控 ContentProvider 的状态地址为：

```text
content://io.github.fplus.highrefresh/state
```

只保存 `initialized`、`enabled` 和 `revision`，不暴露其它配置、下载记录或账号数据。

- 模块自身与主抖音可读取和写入，PowerKeeper 只可读取。
- 身份取自 `Binder.getCallingUid()` 及该 UID 的真实包列表，不能由调用参数自报包名。
- shell、未知应用和极速版不获得该接口的读写权限。
- 首次主抖音读取执行原开关迁移；共享状态已初始化后，旧本地值不能再次覆盖它。
- 设置页加载只读高刷值，不执行一次默认值写入。
- 写入暂失败时，本地 MMKV 保留开关和待同步标记；进程重启后的读取会重试，未确认前不把旧共享值覆盖回本地。
- 原“清空配置”操作同步复位共享高刷开关。
- IPC 响应需要匹配 schema，初始化标记和开关必须是布尔值，修订号必须是非负整数。

PowerKeeper 在独立工作线程连接 Provider 和观察者，原策略线程只使用缓存。开关变更事件立即读取新状态；正常目标场景请求最多每 5 秒合并一次补查。缓存超过 20 秒或读取失败后，新请求保持系统原值；这里没有逐帧轮询或独立周期强制写值。

## 本机系统侧切入点

```text
com.miui.powerkeeper.statemachine.DisplayFrameSetting
private void setScreenEffect(java.lang.String packageName, int fps, int cookie)
```

已核验的字段：

- `mContext`：策略上下文。
- `mCurScreenEnabledId`：当前显示器路由。
- `COOKIE_VIDEO`：正常视频 cookie，本机为 248；运行时读取字段，不把 248 写死为跨版本常量。
- `mCurrentCookie`：回放时确认当前场景没有被其它请求替换。
- `mCurrentDefaultDisplayInfo.mForegroundPackageName`：当前主屏前台包。

本机 PowerKeeper APK SHA-256：

```text
94ecc6f8a5eed07ca5a56ac845e805705cb3cc69d98875ad6ee4a5f6c4bc1e9e
```

方法参数 1 是 fps，参数 2 是 cookie。只改 fps，不对 cookie、返回值、分辨率或其它参数做替换。类、方法或必需字段不匹配时只记录失败并保留原系统策略，不猜测其它 ROM 的混淆名称。

## 策略边界

仅在以下条件同时满足时上调请求：

1. 包为主抖音，当前主屏前台仍为主抖音。
2. 显示器为默认主屏且屏幕处于开启状态，不处理后置副屏。
3. 请求为正常视频 cookie 的正值，低于当前物理分辨率支持的最高有效高刷模式。
4. 共享状态已经初始化、开关开启且缓存未过期。
5. 省电模式关闭，系统热状态已知且低于中等等级。

保留零值清除、负值、已经足够高的值、其它包和其它 cookie；热限制 cookie 253 不改写。收到其它场景后旧视频请求立即失效，回放前再次核验前台包、主屏、当前 cookie 和原 Looper。

不会禁用 PowerKeeper、Joyose 或温控服务，不会直接写全局刷新率键，也不修改系统用户刷新率选择。原方法内部的用户上限和其它系统投票继续生效。

## 原应用侧实现

原应用侧实现保持不变：

- 同分辨率内选择主屏支持的最高有效模式；同率优先当前模式，否则按模式 ID 稳定选择。
- 覆盖 `Window.setAttributes`、`WindowManagerGlobal.addView` 与 `updateViewLayout`。
- Activity 恢复和显示变更后重申窗口请求，参数未变不重复提交。
- Android 11+ 覆盖公开 Java `Surface.setFrameRate` 和 `SurfaceControl.Transaction.setFrameRate` 相关重载。
- 保留暂停清除、无效参数与非无缝切换策略，多显示器归属不明时不猜测 Surface 所属。
- 不改视频源、解码帧数、时间戳、播放速度或刷新率测量结果。

直接 native 帧率请求、首次 Activity 恢复前缓存且不再提交的 Surface 意图以及其它 ROM 私有策略不在新增保证范围内。120 Hz 屏幕不等于每条视频有 120 个不同画面。

## 真机验收

保持设备、亮度、系统刷新率选择、电量模式和测试内容一致，分场景对照开关关闭与开启。每次切换后重启抖音：

| 场景 | 要检查的证据 |
|---|---|
| 推荐页连续上下滑动 | 主屏实际模式、呈现帧间隔与掉帧 |
| 评论区滚动 | 同一分辨率下的主屏实际模式 |
| 停手播放 | 不被正常视频名单重新限制到60 Hz |
| 退出再进入 | 新场景仍提交正确系统请求 |
| 锁屏解锁 | 熄屏不回放旧请求，解锁后重新判断 |
| 重载PowerKeeper或重启手机 | 新Hook加载，共享开关保持原值 |
| 关闭原开关 | 系统侧不再上调，重启抖音后应用侧停止注册 |
| 非抖音与后置副屏 | 不出现本功能对其请求的改写 |

只读证据命令：

```powershell
adb devices -l
adb shell dumpsys package io.github.fplus
adb shell cmd display get-active-mode 0
adb shell dumpsys display
adb shell dumpsys SurfaceFlinger
adb shell dumpsys activity service com.miui.powerkeeper/.statemachine.PowerStateMachineService
adb logcat -d -s Freedom+ Freedom+RefreshSystem Freedom+RefreshSync
adb shell dumpsys gfxinfo com.ss.android.ugc.aweme framestats
```

系统日志中的 `requested` 与 `submitted` 只表示原请求和改写后交给原方法的参数，不能替代实际显示模式。成功判据分别记录“显示高刷”“界面呈现帧”与“视频源帧数”，不以开关开启、临时120数值或单次编译成功作结论。
